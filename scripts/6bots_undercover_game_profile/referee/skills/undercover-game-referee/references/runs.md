# 两个临时自定义协作的形状

YAML 由 `render-speak-run` / `render-vote-run` 生成，**不要手写**。这份文档解释它们为什么长这样，方便出问题时判断是不是渲染出了偏差。

## 发言：传递闭包，不是链

存活玩家按座位顺序 `s1..sk`，加一个我的汇总节点：

```text
s1 ─┬──────────────────────────┐
    └→ s2 ─┬───────────────────┤
           └→ s3 ─┬────────────┤
                  └→ ... ─┬────┤
                          └→ sk ┤
                                ↓
                            collect（我，final_output）
```

第 i 个发言节点的 targets = **它后面所有发言节点 + collect**。

为什么不是简单的链：节点提示里只包含**直接父节点**的产物。`s1→s2→s3` 会让 s3 看不到 s1 说了什么。把前面所有人都连成父节点，后手才能拿到本轮完整发言，collect 才能一次拿到全部 k 份。

人类玩家的位置是一个 `human_input` 节点，没有 assignee、没有 binding，超时给足 15 分钟。

每个发言节点的 instruction 里都带一段**本轮钝度**（`bluntness_block`）。`forbid_line` 管的是
字面泄词，钝度管的是语义泄词——第一轮就把词描述到只对应一件东西，卧底当场暴露，整局
一轮就结束。钝度按轮次收敛（5 → 3 → 2），信息也就按轮次释放。第一位发言者没有参照，
它的指令里会额外说明本轮的钝度由它定。

发言运行的入口天然是第一位发言者，不是我，所以它没踩过投票运行那个坑。别把它改成
由我开场。

## 投票：扇出再汇合

```text
vote_open（首位存活玩家）─┬→ vote_s1 ─┐
                          ├→ vote_s2 ─┤
                          ├→ vote_h  ─┤   ← 人类的票也在这一层，和 Bot 同时进行
                          └→ vote_sk ─┘
                                       ↓
                                    tally（我，final_output）
```

- `vote_open` 存在的唯一理由：运行必须有**唯一零入度入口**（服务端硬性校验，多于一个直接拒收）。所以必须有个人当门房，而门房的产物会流给全部投票节点——所以它的 instruction 写死成「只输出两个字：开始」，零信息量。
- **入口节点绝不能派给我。** 这是踩过的坑：我是在自己的一次激活里同步提交运行的，运行一启动就把入口节点派回我的会话通道，而那条通道正被提交它的那次激活占着。节点排在我自己后面等我让路，一旦通道没及时释放就永远等不到，整个运行随它超时失败——而运行失败**不会**唤醒我，游戏就无声地停在那里。
- 门房挑第一位存活 Bot，不挑已出局的：已出局玩家的通道要留给看门狗任务（S3），两个都往那儿塞就是换个地方再犯同一个错。代价是门房结束的瞬间它自己的投票节点会派回同一条通道，那个窗口只有零点几秒，用更长的 `node_timeout_ms` 兜住。
- 所有投票节点并行，彼此看不到对方的票。每个人的词写在自己节点的 instruction 里，公开的发言史走 `--input`。
- **投票节点只要票号，不要理由。** 一条理由就是"拿我的词比对他的话"的结果，被我在开票时念出来，等于把那个玩家的词属性广播给全场——第一轮结束信息就透明了。所以玩家的唯一判断依据是 `--input` 里所有人全部历史轮次的发言。指令是软的，`votes-set` 还会把票面规范化成票号，就算有人多写了半句也到不了主持稿里。
- `tally` 是汇合点，BCS 会等齐全部上游才派给我。全场只有我能同时看到所有票。它派给我的时候我的通道早就空了，所以汇合节点派给自己是安全的——不安全的只有入口节点。

## 两个运行为什么不合并

合并成一个运行会让"发言转述"变成中间节点的产物——而中间节点的产物只进副屏，不进群聊。人类就看不到发言转述了，整局在聊天里只剩一条最终结果。

分成两个运行，发言转述才能作为第一个运行的 `final_output` 自动发成群消息。代价是中间需要人类说一声才能开投，这一拍同时也是他读转述、想清楚的时间。

## 硬约束（服务端会拒绝的写法）

- 顶层只允许 `name`、`metadata`、`participants`、`runtime`；不能有 `api_version` / `id` / `version`。
- `runtime.kind: state_machine`、`state_machine.version: 1`、`graph_mode: acyclic`。
- 只能用 `bot_task` 和 `human_input`；不能用 `initial_node`、`variables`、`events`、`guard`、`action`、`output_contract`、`input_schema`。
- 唯一零入度入口、唯一 `final_output` 出口，所有节点从入口可达且能到达出口。
- `human_input` 不设 `assignee` / `max_attempts` / `final_output`，但**必须**显式给 `node_timeout_ms`。
- 一个运行里只能有一个 `human_input` 节点。
- 提交时人类必须处于 Present。
- 真实 Bot UUID 只出现在 `--binding`，不写进 YAML。

## 超时与重试为什么是这两个数

Bot 的会话通道是串行的：同一时刻只跑一个激活，其余排队。通道偶尔会在一次激活结束
后没及时释放，节点任务就一直排在队里不动，要等 Bot 侧的自愈把通道抢回来——那个
窗口是**分钟级**的。所以：

- `node_timeout_ms` 默认 **420000**（7 分钟），必须明显大于那个自愈窗口。短于它的话
  BCS 先判死、自愈后到，节点产物变成没人认领的孤儿，还会迟到几十秒后突然冒到群里。
- 派给我的节点（`collect` / `tally`）和入口那位的投票节点用 **600000**。我的通道最挤：
  人类的自由聊天、节点任务、以及我自己 `final_output` 的回灌都走这一条。
- `max_attempts` 固定 **1**。重试对「通道堵住」这类故障毫无作用，只会让同一个节点排
  两份，排空时还可能逆序执行，在群里留下重复播报和一条空回复。真正的瞬时失败由
  Bot 侧自己重试。

这几个数由 `undercover.py` 顶部的常量统一给出，回归测试会逐条卡住下限，不要在
YAML 里手动调小。

`scripts/lib/undercover_run_check.rb`（仓库里的回归测试）会对渲染结果逐条校验以上全部。
